## 已复现问题

### A01 · P1 · 修改需求后继续使用旧值，日期数字被当成预算

证据：真实流式接口。

1. 输入：从温州去哈尔滨，2026-12-01，3天，1人，预算10000元，希望美食。
2. 收到需求整理后，输入：日期改成12月5日，改成5天，2人，预算5000元。
3. 实际：ready=true，返回12月1日、3天、1人，预算变成12元；可生成的trip_request也使用这些错误值。

预期：12月5日、5天、2人、5000元。独立调用提取器时，单独改日期、人数、天数、预算也没有可靠应用最后一次修改。collect_trip_intake对完整历史多处使用首次正则匹配，且将上一条含“总预算”的确认摘要视为预算问句，随后用回答中的第一个数字12作预算。

定位：backend/app/agents/intake.py:327、345、349。

验收条件：同一条消息可同时改四个字段；日期数字不参与预算识别；否定旧值后不能恢复旧值；确认文字、trip_request和持久化状态一致。

### A02 · P1 · 明确排除的菜系仍被用于查询

证据：真实地图查询及回复。

上下文：哈尔滨、中央大街、锅包肉。输入“不要锅包肉了，推荐素食餐厅”，返回老厨家等一般餐饮候选，未体现素食筛选或说明无法确认素食条件。代码仍从整句中提取“锅包肉”作为查询词，不理解否定，也没有提取“素食”。

定位：backend/app/agents/dining.py:49。

验收条件：否定项不进入正向检索；明确饮食限制应进入检索与展示，无法确认限制时说明具体未核对项。不能将普通餐饮候选呈现为已符合素食等条件的结果。

### A03 · P1 · 上一条助手回复过长，会使下一条消息直接被拒绝

证据：真实接口。构造一条4250字的历史助手回复，再发送“第二天轻松点”，接口返回HTTP422，没有进入对话流程。

定位：backend/app/schemas/domain.py:43。客户端每次提交整个历史；助手输出与历史消息输入的4000字上限没有协调。

验收条件：长回复后仍能追问。用户输入限制、助手历史限制及上下文裁剪策略分开，超限时有可理解且能继续操作的反馈。

### A04 · P1 · 历史中的“明天”随打开日期漂移

证据：需求提取器直接调用，消息附带时间。

原消息时间为2026-11-09，内容“明天从温州去哈尔滨”。11月10日重建需求时，期望出发日仍是11月10日，实际变为11月11日。created_at没有用于相对日期的解析基准。

定位：backend/app/agents/intake.py:332及相对日期循环。

验收条件：相对日期在表达时解析并保存；恢复历史或继续追问时不重新平移。跨年和跨时区同样保留原确认日期。

### A05 · P1 · 完整规划缺少交通时间与活动安排之间的约束

证据：真实三天温州→杭州规划，2人、预算6000元、美食与轻松散步、allow_mock=false，约15.41秒返回。

- D1选择22:04出发、23:23抵达的交通候选，随后仍安排“入住并熟悉酒店周边”“品尝当地特色晚餐”，没有解释深夜抵达对日程的影响。
- D2安排09:30千岛湖、14:00西溪；路段核对未成功，仍输出固定14:00活动时间。
- 3天的具体地点数量为[0,2,0]，美食偏好主要停留在“午餐与休息”等泛化文字。

系统确实返回partial及路线/开放时间WARNING，不能说它声称全部核验通过；但警告没有阻止或调整依赖该路线的固定安排。

验收条件：交通到达时间影响当天可用时段；路段无法核对时不能继续输出看似已经可衔接的精确时间；偏好应体现为实际安排。完成反馈应明确未完成部分。

### A06 · P2 · 餐厅“换一家”掉回泛化聊天并扩大修改范围

证据：真实聊天及意图识别。

已给出老厨家后输入“换一家，不要这家”，没有dining_search阶段。实际重写D1—D3，又问“需要我推荐具体店名吗”，未直接返回另一个可核对的店。“有没有便宜点的”也未命中餐厅查询。

定位：backend/app/agents/dining.py:14—15及会话分类路径。

验收条件：继承上一次查询类别、排除已拒绝的店；只替换被要求的候选，不重写整段日程；涉及低价要求时不能编造价格。

### A07 · P2 · 停止生成后，刚发送的问题未被保存

证据：真实流式连接收到首个progress后断开，再GET该测试对话，messages数量为0。

这复现了停止/刷新对应的服务端行为；未实际点击浏览器按钮。客户端有停止时中断请求的代码，而用户消息只在完整回复持久化时共同保存。

验收条件：用户消息在接收时保存；停止只影响未完成的助手回复。刷新不丢已发送问题，停止状态可见且不会伪装为生成失败。

### A08 · P2 · 需求齐全后切换/刷新，生成入口状态不能恢复

证据：真实接口加前端代码核对。

首次ready=true；GET对话详情不含trip_request。openConversation将request清空，因而已有需求尚未正式规划时无法恢复原“生成行程”入口，只能再发消息触发。

定位：frontend/src/pages/PlannerPage.tsx:109。

验收条件：恢复对话时还原需求状态与生成入口；不能仅恢复聊天文字。

### A09 · P2 · 英文能回复，但没有进入同等结构化规划流程

证据：真实英文完整需求，约6.12秒返回。

已明确出发地、目的地、日期、人数、预算和偏好，返回英文三天文字安排，但ready=false、collected={}、trip_request=null，无法获得中文流程同等的正式生成入口。还出现“no live data available here”的笼统描述，本次没有search阶段。

定位：backend/app/api/routes.py:321、374，英文强制走普通建议分支。

验收条件：语言只改变表达，需求收集、正式规划、预算和来源状态等能力保持一致。

### A10 · P2 · 不确定回答和省份仍可能被当成具体城市

证据：需求提取器直接调用。

- 问“你想去哪个城市？”后答“都行吧”，实际ready=true、destination=都行。
- 完整需求中目的地为江西，实际ready=true；仅现有少数区域名称会触发具体城市确认。
- “不去哈尔滨了，改去成都吧”实际提取器仍可能得到“哈尔滨了”；明确否定旧目的地也没有可靠清空。

验收条件：不确定表达不能变成地点；区域级目的地进入城市/路线澄清；否定与替换按消息顺序应用。

### A11 · P2 · 输入错误被包装成泛化服务失败

证据：真实流式接口。把人数写成0人，HTTP200流中返回“JARVIS 暂时无法处理这条消息，请重试。”没有解释人数必须至少1人。

验收条件：明确指出可修正字段；输入错误不建议无效重试，不与供应商或网络故障混为一谈。

### A12 · P2 · 导出没有保留完整预算和待核对信息

证据：真实规划保存/恢复/Markdown导出。

页面完整计划的total_cost_cny为6000，未选候选合计为0；导出仅含“已选费用合计0元（不含尚未选择的项目）”，不包含完整预算明细、路线未核验等关键说明。0元的已选合计本身算术正确，问题是完整行程导出缺失费用和验证上下文。

验收条件：导出分别保留总预算、估算明细、已选合计与待核验事项，含义与页面一致。
