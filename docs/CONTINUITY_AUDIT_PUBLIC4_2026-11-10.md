日期2026-11-10；应用/API/JS包`0.6.0-public.4`，Python包`0.6.0rc4`。本轮继续从public.3挑刺，重点检查跨功能状态一致性。

## 新确认并修复

| 问题 | 修复 |
| --- | --- |
| 同一条消息说“重新开始”并给新条件，新条件被忽略；取消同时修改预算也会漏掉后半句。 | 先应用控制指令，再应用同条消息中的其余明确条件，作为一次可撤销修改。 |
| 英文“不要改预算，改目的地”把两个字段都锁住。 | 英文否定保护按分句作用，不冻结另一个明确修改。 |
| 调整第二天有时只返回条件摘要；撤销还可能误退上一次预算修改。 | 每日安排编辑进入行程咨询，和条件编辑使用一致的修改边界；保存实际工作区快照，撤销同时恢复条件、日程和相关估算状态。 |
| 撤销预算后仍显示待修改，已保存完整行程还反复出现生成入口。 | 恢复之前的日程状态；现有完整计划与条件一致时不重复提示生成。 |
| 重置后旧日程、选项和费用可能被用于新旅行；给新城市建议时把旧日期/价格套了过去。 | 旧行程明确标为上一趟，不进入新咨询上下文；清空新旅行的旧候选和复核缓存。接受新旅行日程草案时解除旧TripRecord关联，保留原始记录，不把旧报价重标成新城市报价。 |
| 暂停期间每日安排仍能修改，恢复后又留下假的待更新状态。 | 暂停时不调用每日改写模型、不发布修改；界面、目录、详情和导出明确显示已暂停。 |
| 生成后迟到的保存请求可覆盖重置或新条件；同一计划重试保存又可能覆盖后续每日修改。 | 保存前核对当前条件及规划状态，不匹配返回409；同一已保存计划重试只返回当前工作区，不重新覆盖日程。 |
| 模型只写D1/D2时悄悄删掉原D3；新草案少天数时也不清楚。 | 根据已确认天数应用补丁，保留未改动日；明确缩短天数后才裁掉尾部。新草案不完整时显示未完成，不悄悄改变用户要的天数。 |
| “第二天”“第3位同伴”被当成总天数或总人数。 | 序数不再写入总量字段。 |
| 每日安排改了，原计划的PASS仍可能保留。 | 当前展示派生视图标为WARNING并提示重新核验路线、营业及预约；不改写原始TripRecord的验证记录。 |
| 酒店询问后直接回答日期/城市，接不上查询；日期/城市还可能改坏旅行条件。 | 继承当前酒店查询及必要原文，规范缺城市/日期的追问，并与旅行条件隔离。停止查询不再触发新查询；一般旅行城市问题不会误当酒店追问。 |
| 重置后撤销，供应商查询仍停留在被重置的会话范围。 | 查询上下文与需求使用同一套重置/撤销范围，不借用未恢复的旧条件。 |
| 退房省略年份时可能取当前年，和明确的未来入住年份不一致。 | 同条日期表达按入住日承接年份，跨年退房正确进到下一年。 |
| 旧计划待修改时，当前已选费用仍按旧预算算；重置后的新费用还混入旧计划。 | 当前候选按当前预算计算；上一趟计划保持自己的历史估算，和新旅行候选分开。 |

## 撤销边界

保存最近20次有效修改的工作区快照，撤销不会删除或倒退聊天消息、请求标识和发送时间。旧记录或已超出保留范围的修改没有快照时，明确说明未撤销，保留当前条件与安排；服务端记录该次未应用操作，避免下一轮重新解析时再误执行。旧客户端省略这个服务端标记时，也保留已存状态；新请求不能伪造标记来跳过条件修改。
